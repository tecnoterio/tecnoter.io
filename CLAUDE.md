# Tecnoter.io - AI Assistant Context

## Project Overview
A retro-futuristic terminal interface for tecnoter.io built with:
- **Hugo** static site generator (Go)
- **Rust/WASM** for terminal shell logic
- **Vanilla JS** for UI, terminal emulation, and WASM integration

## Architecture

```
├── content/              # Hugo content (posts, pages, terminal commands)
├── themes/tecnoter.io/   # Custom Hugo theme
│   ├── static/js/        # Client-side JS modules
│   │   ├── terminal.js   # Main terminal entry point
│   │   ├── commands.js   # Command implementations (JS fallback)
│   │   ├── system.js     # State management, WASM init
│   │   ├── ui.js         # DOM rendering, input/output
│   │   ├── listeners.js  # Event handlers
│   │   ├── bbs.js        # BBS interface
│   │   └── wasm/         # WASM output (generated by wasm-pack)
│   └── layouts/          # Hugo templates
├── shell_wasm/           # Rust crate compiled to WASM
│   ├── src/
│   │   ├── lib.rs        # WASM entry point: process_input()
│   │   ├── shell.rs      # Command routing, login flow
│   │   ├── state.rs      # Serialization types (SystemState, Fortune, etc.)
│   │   ├── commands/     # Individual command implementations
│   │   └── fs.rs         # Virtual filesystem
│   └── Cargo.toml
├── data/                 # TOML data files (fortunes, site content)
└── public/               # Hugo output (served by `hugo server`)
```

## Key Data Flow

1. **Hugo builds** `index.json` from content + data/fortunes.toml
2. **Browser loads** `terminal.js` → fetches `index.json` → populates `state`
3. **WASM initialization** via `system.js:initWasm()` → loads `tecnoter_shell.js`
4. **User input** → `processWithWasm(line)` → `wasm.process_input(state, line)`
5. **WASM returns** `WasmResponse { lines, state, handled }` → UI renders, state synced

## Critical Types (must match between JS and Rust)

**Rust** (`shell_wasm/src/state.rs`):
```rust
struct SystemState {
    cwd: String,
    current_user: String,
    login_state: String,  // UNINITIALIZED, BOOT, LOGIN, PASSWORD, PROMPT, BBS_MAIN, BBS_PAUSE, etc.
    posts: Vec<Post>,
    pages: Vec<Page>,
    socials: Vec<Social>,
    fortunes: Vec<Fortune>,  // NOT Vec<String>!
    system_info: SystemInfo,
    version: String,
    return_state: String,
    booted: bool,
    is_authenticated: bool,
    debug_mode: bool,
    mail_recipient: Option<String>,
}

struct Fortune { text: String }  // matches JSON: {"text": "..."}
```

**JSON** (`public/index.json`):
```json
{
  "fortunes": [{"text": "Simplicity is the soul of efficiency."}, ...],
  "posts": [...], "pages": [...], "socials": [...],
  "systemInfo": {...}
}
```

## Known Issues / Gotchas

1. **WASM deserialization**: `fortunes` in JSON is array of objects, NOT strings. Rust must use `Vec<Fortune>` with `#[serde(rename_all = "camelCase")]`.

2. **Hugo serves from `public/`**: WASM built to `themes/tecnoter.io/static/js/wasm/` must be copied to `public/js/wasm/` for live reload. Or run `make dev` which handles both.

3. **State serialization**: Uses `serde_wasm_bindgen` with `camelCase` rename. JS state keys must match (e.g., `loginState` ↔ `login_state`).

4. **Terminal modes**: `TERMINAL` (CRT) vs `HUB` (static). Controlled by `state.systemMode` and body class `mode-terminal`.

5. **Login flow**: UNINITIALIZED → BOOT → LOGIN → (PASSWORD for admin) → PROMPT/BBS_MAIN. State persisted in `sessionStorage`.

## Adding New Commands

1. **Rust** (`shell_wasm/src/commands/newcmd.rs`):
   ```rust
   pub fn handle(state: &SystemState, args: Vec<&str>) -> String { ... }
   ```
2. Register in `shell.rs` command routing
3. Rebuild: `make build-wasm`
4. **JS fallback** (optional): Add to `commands.js` switch in `run()`

## Testing WASM Logic Locally

```bash
cd shell_wasm

```

## Debugging Tips

- Open browser DevTools → Console: WASM errors appear as `WASM: Critical state deserialization failure: ...`
- Enable `?debug` in URL or click LOGS knob for verbose output
- `window.terminalSystem.ping()` in console tests WASM directly
- Check `state` object in console matches Rust `SystemState` structure
