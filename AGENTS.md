# AGENTS.md

Context for AI assistants working in this repository. Read this before editing.

## What this is

A dual-mode site: an interactive CRT terminal and a plain static website, sharing
one body of content. The terminal's shell is Rust compiled to WebAssembly; the
site is built by Zola.

```
├── content/            # Markdown. The single source of truth
├── data/               # fortunes.toml, site_content.toml
├── shell_wasm/         # Rust -> WASM. The terminal's command processor
├── templates/          # Zola / Tera templates
├── static/             # js, css, fonts. WASM is built into static/js/wasm
├── scripts/zola/       # index.json generation, parity check, link check
├── tests/golden/       # committed JSON reference (see "Parity")
├── zola.toml
└── Makefile
```

## Commands

```bash
make build          # WASM -> link check -> Zola -> index.json -> parity check
make serve          # dev server on http://127.0.0.1:1111
make dev            # dev server + WASM rebuild on change
make build-wasm     # Rust -> WASM into static/js/wasm
make check-links    # verify every external link still resolves
make accept-content # after an intentional content edit, see "Parity"
```

## Rules

- **Never edit build output.** `public/` and
  `static/js/wasm/` are generated and gitignored. Commit sources only.
- **WASM output goes to `static/`, not `public/`.** `zola build` clears
  `public/`, so building straight into it is undone on the next run.
- **Rust and JS types must match exactly.** `serde(rename_all = "camelCase")` on
  every struct that crosses the boundary; JS state keys are camelCase.
- **`group` is unusable as a front-matter key.** Tera parses `page.group` as the
  built-in `group` filter, so the field silently evaluates to nothing. Zola's nav
  comes from `[extra].nav` in `zola.toml` instead.
- **Content uses TOML front matter** (`+++`), not YAML.

## The terminal's data feed

The terminal reads two kinds of JSON, both generated by
`scripts/zola/build-index-json.py` after the Zola build. Zola has no
per-page output format, so they cannot be templates.

| File | Read by | Purpose |
|------|---------|---------|
| `index.json` | `static/js/system.js` | posts, pages, socials, fortunes, systemInfo |
| `<section>/<slug>/index.json` | `shell_wasm/src/commands/cat.rs` | page body, for `cat` |

Consequences worth remembering:

- `fortunes` is `Vec<Fortune>`, **not** `Vec<String>`. The JSON is
  `[{"text":"..."}]` and `Fortune` is a struct with a `text: String` field. This
  mismatch caused a deserialization failure once already - if you see
  `WASM: Critical state deserialization failure`, suspect a type drift first.
- Adding a page needs nothing extra - the script walks `content/`. Adding a
  *type* means updating both the Rust struct and the script.
- `cat` fetches asynchronously via `spawn_local`, so a missing file reports an
  error line after the prompt returns, not at the prompt.

## Deployment paths

Every asset reference, the `index.json` fetch, and the URLs inside that file go
through a base path: empty on the live site, `/<repo>/pr-<n>/` for a pull request
preview. It reaches the templates via `get_env(name="TECNOTER_BASE")`, and
`static/js/terminal.js` reads the same value from `window.SITE_BASE`.

The Rust side needs nothing: `cat` builds its fetch URL from the `url` field in
`index.json`, so prefixing that one field covers it, and `bbs.js` and
`commands.js` with it. `check-parity.py` strips the prefix before comparing, so
the gate checks content rather than deployment path.

`make preview N=42` reproduces a preview build locally.

## Parity

`make build` runs `check-parity.py`, which compares the generated JSON against
`tests/golden/`. **Any content edit fails the build**, because the
reference is a snapshot rather than a live comparison. After an intentional edit:

```bash
make accept-content
```

The reference was seeded from the Hugo build that preceded Zola, so it still
encodes how `cat` output was formatted at the time of the port - including
several non-obvious Markdown-to-plaintext rules (headings merging into their
paragraphs, hard line breaks, smartypants). If parity fails on a page whose
prose did not change, the converter probably regressed.

## Adding a command

1. `shell_wasm/src/commands/<name>.rs` with `pub fn handle(state, args) -> String`
2. Register it in `shell_wasm/src/shell.rs`
3. `cd shell_wasm && cargo build` to check
4. `make build-wasm` to get it into the browser

## Layout

The index, the hub, and the standalone `/terminal/` page use separate templates.
`partials/hub_frame.html` and `partials/terminal_frame.html` are shared, and
`terminal_frame.html` includes `hub_frame.html` - so hub chrome appears on every
page. Mode switching happens in `static/js/system.js` via `state.systemMode`.
