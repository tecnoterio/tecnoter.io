# Hugo → Zola Migration

Status: **complete.** Hugo is deleted. Zola builds the site from the repository
root and CI deploys it. Everything below was verified against Zola 0.23.6 by building
it, not taken from docs.

---

## What actually works

```bash
make build   # WASM → Zola → index.json → parity check
make serve   # http://127.0.0.1:1111
```

Verified output: 12 pages, 2 sections, plus `index.json`, per-page `index.json`,
RSS, sitemap, search index. `scripts/check-parity.py` asserts the generated JSON
matches the committed golden file and gates `make build`.

## The safety net outlived Hugo

`scripts/check-parity.py` originally compared against a live `hugo` build. That
made the check circular: deleting Hugo would have deleted the reference and
with it the only proof the port is faithful.

The fix was to record the Hugo output into `zola_spike/tests/golden/` — 13
JSON files, ~52K, committed. The check now runs against that, and was verified
to pass with Hugo entirely absent, and to fail when a golden file is tampered
with.

The script that seeded it has since been deleted, so the reference is now
advanced with `make accept-content`.

## The eight things that bit

These are the actual migration costs. Everything else was mechanical.

### 1. `templates/_default/` does not exist

Hugo's fallback templates have no Zola equivalent. Miss this and Zola silently serves
its own placeholder page instead of erroring.

| Hugo | Zola |
|------|------|
| `layouts/_default/single.html` | `templates/page.html` |
| `layouts/_default/list.html` | `templates/section.html` |

### 2. No `jsonify` / `tojson` filter

Hugo's `| jsonify` has no Tera equivalent. Anything that embedded JSON into a
`<script>` tag has to be rebuilt as hand-written JS literals, or moved out of
templates. The terminal's `window.siteFortunes` / `window.siteSocial` globals are
affected.

### 3. `get_section` takes a file path, not a slug

```tera
{% set posts = get_section(path="posts") %}          {# FAILS #}
{% set posts = get_section(path="posts/_index.md") %} {# works #}
```

`zola check` reports 2 sections and still lets you build. The failure only surfaces
at render time as `Section 'posts' not found`.

### 4. No property chaining on a function call

```tera
{% for p in get_section(path="posts").pages %}   {# parse error #}
{% set s = get_section(path="posts") %}          {# works #}
{% for p in s.pages %}
```

### 5. Front matter is on the page, not under `.extra`

`.Site.Params` / `page.Params` / `page.extra` are Hugo-isms. Zola exposes front-matter
keys directly: `page.title`, `page.nav`, `page.weight`.

**And `group` is unusable as a key.** Tera parses `page.group` as the built-in
`group` filter, so the field silently evaluates to nothing. Any Hugo front matter
key that collides with a Tera filter name must be renamed. We use `nav`.

### 6. No per-page multi-format output

Hugo's `layouts/index.json` produces `/index.json` on demand. Zola has no equivalent —
`output_format` + `permalink` in front matter produced `public/index-json/index.html`
and was dropped. **`index.json` is now generated by `scripts/build-index-json.py`**
after the Zola build, reading the same Markdown front matter.

### 7. `zola build` wipes `public/`

`make build-wasm` originally targeted `public/js/wasm` and Zola deleted it on the
next build. The WASM output now targets `zola_spike/static/js/wasm/`, which Zola
copies into `public/` like any other static asset.

### 8. `cat` in the terminal needs per-page JSON

`shell_wasm/src/commands/cat.rs` fetches `<url>index.json` to render page content.
Hugo produced those from `layouts/_default/single.json`. Zola has no per-page
multi-format output, so `scripts/build-index-json.py` now emits
`pages/<slug>/index.json` and `posts/<slug>/index.json` alongside the site index.

The `content` field has to match Hugo's `.Plain` exactly, which is a Markdown
to-plaintext conversion with three non-obvious rules:

- a heading and its paragraph form **one** line
- a heading with no body of its own merges into the next line
- a paragraph following a list joins the list's line

Getting these wrong produces output that renders fine but differs from the Hugo
build, which is invisible unless you diff it — hence `scripts/check-parity.py`,
wired into `make build` as a gate.

## Smaller differences worth noting

| Hugo | Zola |
|------|------|
| `.Site.Title` | `config.title` |
| `.RelPermalink` | `page.relative_path` (absolute `page.permalink` is wrong — it embeds `base_url` and breaks local serving) |
| `.Content` | `page.content \| safe` |
| `where .Site.RegularPages "Section" "posts"` | `get_section(path="posts/_index.md").pages` |
| `partial "x.html" .` | `{% include "partials/x.html" %}` |
| `range` / `if` | `{% for %}` / `{% if %}` |
| `.Site.SearchIndex` | no server-side search; client-side via `search_index.en.js` + elasticlunr |
| `[params]` | `[extra]` |
| `[[menu.main]]` | no built-in menu; used `[extra].menu_main` |

Ordering also differs. Hugo sorts pages by `weight` then title, and posts by date
descending with title as the tiebreak. `build-index-json.py` reproduces both, because
the terminal's `ls /pages` output depends on it.

## Deliberate deviations

- **Nav links live in `zola.toml` `[extra]`, not page front matter.** The
  front-matter-driven loop fought Tera's parsing rules repeatedly (see #5), and two
  static lists in config is honestly clearer. If pages get added later, move back.
- **`index.json` is a script, not a template.** No Tera equivalent exists.
- **Search is a JS page**, matching Zola's own client-side model.
- **`/terminal/` is a plain `templates/terminal.html`** with a module shim, rather
  than the Hugo `{{ define "main" }}` block. Zola has no block-define mechanism.

## One content directory, not two

While Hugo was still live, `zola_spike/content` was a **symlink to
`../content`**, so both generators read the same files and a content edit was
picked up by both with no sync step. It has since been flattened, so there is
one directory and no symlink. Three things had to be true for the symlink:

1. `content/posts/_index.md` and `content/pages/_index.md` exist. Zola needs a
   section index to recognise a section; Hugo does not, and tolerates them
   without adding pages. Verified by diffing the Hugo output before and after —
   identical.
2. `content/terminal/commands/{uptime,whoami}.md` have front matter. They had
   none, and Zola refuses to parse a content file without it. Nothing references
   them; they look like leftovers from an earlier phase and are candidates for
   deletion.
3. The `group` front-matter key is left alone. Hugo's `hub_frame.html` reads
   `.Params.group` to build its nav. Zola cannot use that key — `page.group`
   parses as Tera's built-in `group` filter — but it does not need to, because
   its nav comes from `[extra].nav` in `zola.toml`. So the two coexist.

## Taxonomy pages

`/tags/*` and `/categories/*` needed work: `fs.rs` advertises those directories
in `ls /`, but Zola emitted nothing, so they 404'd.

Two things had to line up:

- **Taxonomy names must be plural** in `zola.toml`, otherwise the paths are
  `/tag/` not `/tags/` and stop matching Hugo's URLs.
- **Terms come from a `[taxonomies]` table in page front matter**, not from a
  top-level `tags` key. Hugo wants the top-level key. Both shapes now coexist in
  the three post files, so each generator reads what it needs:

  ```toml
  +++
  title = "Hello World"
  tags = ["intro", "hugo"]        # Hugo
  categories = ["general"]
  [taxonomies]                    # Zola
  tags = ["intro", "hugo"]
  categories = ["general"]
  +++
  ```

Zola also silently produces nothing if the templates are missing - no error, no
pages. The generic fallbacks are `taxonomy_list.html` (the `/tags/` index) and
`taxonomy_single.html` (a term page), and both receive `terms` / `term`, not
`page`.

Verified: all 8 taxonomy URLs now match Hugo's set exactly.

**Known limitation, present in both generators:** the taxonomy pages render the
standard hub frame, whose main column falls through to the biography fallback -
it does not list only the posts in that term. That is existing `hub_frame.html`
behaviour, not a migration regression. Making it term-aware is a separate
feature.

## Accepting intentional content changes

The parity reference was seeded from Hugo, which means any real content edit
legitimately moves it and `make build` fails. That is correct behaviour for a
regression check, but it needs an escape hatch:

```bash
make accept-content   # adopt current output as the baseline
```

The Hugo-derived golden file is the *proof* that the port is faithful. Once that
has been established, `accept-content` is how the baseline moves forward.


- The `menus` in `[extra].menu_main` are unused; no template consumes them yet.
- Colour-mode CSS classes (`mode-amber`, `mode-green`, `mode-bw`) come from the
  hardware-controls partial and were carried over unchanged — not verified in a
  browser, only that the markup is present.
- The Zola site has not been checked in a real browser against Hugo side by side.
- `content/terminal/commands/{uptime,whoami}.md` are referenced by nothing. They
  only needed front matter added to satisfy Zola's parser, which suggests they
  are dead weight from an earlier phase.

## Outcome

The port was roughly 10 template files. Every obstacle turned out to be a
Tera/Hugo syntax mismatch rather than an architectural one.

What changed: `hugo.toml`, `themes/`, `layouts/`, `archetypes/` and
`hugo.yml` are gone. `Makefile` is the Zola one, so `make build` and
`make serve` work the same as before. `zola.yml` replaces the Hugo workflow
in CI.

What did not change: the terminal, the Rust/WASM shell, the site URLs, the
dual-mode behaviour, or anything the user sees.

The Zola project was first built in a `zola_spike/` subdirectory while Hugo
was still live, then flattened into the repository root once Hugo was removed.
`content/` and `data/` no longer need to be symlinked, because there is only
one copy of each.

## Rollback

Every removal is a normal commit, so `git revert` restores Hugo:

```
git revert 4b392ed 17540c6    # restores the theme, config and hugo.yml
git revert 83879a9            # removes the Zola pipeline
```

The parity reference in `tests/golden/` is the quickest way to tell whether a
Zola change altered anything Hugo used to produce.
